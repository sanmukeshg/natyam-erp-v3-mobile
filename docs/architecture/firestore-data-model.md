# Firestore Data Model — Identifiers & Document Structure

This document explains two things that apply across every Firestore collection in NATYAM ERP, not just one module: how a record is identified, and how its data is structured. It was written alongside the Student Management migration (Milestone 3) but is not specific to Students — treat it as the standing reference for every future module migration.

See also: [ADR-014](adr/ADR-014-Firebase-Authentication-and-Firestore.md) (why Firestore at all), [docs/migrations/STUDENT_MODULE_MIGRATION.md](../migrations/STUDENT_MODULE_MIGRATION.md) (the Students-specific migration record, and the template for future ones).

## Document Identifier Standard

Every Firestore collection in this project follows one rule: **the document ID is a purely technical, internal detail, and the business identifier is a separate field.**

- **Firestore Document ID** — auto-generated (via `addDoc`), or in one deliberate exception (`users`, keyed by email — see below) a stable technical key. Never displayed anywhere a person reads: not in the UI, not in reports, not on a receipt or certificate. Code should treat it as an opaque string.
- **Business Identifier** — a human-readable, sequential code stored as an ordinary field on the document, generated by the centralized sequence generator (below). This is what appears in the UI, in exports, on printed documents, and in conversation ("call up STU000412").

| Collection | Business identifier field | Format | Status |
|---|---|---|---|
| `users` | `userCode` | `USR000001` | Generator exists (`nextUserCode()`); not yet wired into user creation — see Known Gaps below. |
| `students` | `studentCode` | `STU000001` | Live — generated automatically inside `create()`/`createMany()`. |
| *(future)* branches, batches, admissions, receipts, expenses | `branchCode`, `batchCode`, `admissionCode`, `receiptNumber`, `expenseCode` | `BRN000001`, `BAT000001`, `ADM000001`, `RCP000001`, `EXP000001` | Not yet migrated to Firestore. Adopt the same pattern when they are. |

### The one exception: `users` is keyed by email, not an auto-generated ID

`users` documents use the person's lowercased email address as the Firestore document ID, decided and documented in `js/data/users.repository.firestore.js`. This predates the Document Identifier Standard (it shipped in Milestone 2) and is **not** being retrofitted to match it, for two concrete reasons that still hold:

1. An Administrator provisions a person by email *before that person has ever signed in* — their eventual Firebase Auth UID doesn't exist yet, and an auto-generated Firestore ID would be equally unknowable in advance, so there'd be no way to address "the record for someone who hasn't signed in yet" if the ID were opaque.
2. `firestore.rules` needs a direct, computable path to "the caller's own document" to authorize efficiently. Firestore rules cannot run an arbitrary "find where email = X" query the way application code can — keying by email (always available from `request.auth.token.email`) makes that path always `users/{their email}`.

`userCode` still exists as the *business* identifier for Users, displayed identically to `studentCode` — only the document ID differs from the standard, and only for this one reason-justified case. Every future collection should default to an auto-generated document ID unless it hits the same "must be addressable before it's fully provisioned, and rules need a direct path" constraint `users` did.

## Centralized Sequence Generator

`js/data/sequenceGenerator.firestore.js` exports one function, `nextCode(name, prefix, padLength = 6)`, used by every repository that needs a business code:

```js
export async function nextCode(name, prefix, padLength = 6) { … }
```

- One shared document, `meta/counters`, with one field per sequence (`{ userCode: 5, studentCode: 12 }`).
- Every call runs inside a Firestore transaction: read the current value, increment it, write it back, return the formatted code — atomic, so two people creating a record in the same instant can never be handed the same number.
- **Do not write a second counter transaction anywhere else.** If a new module needs a business code, it calls `nextCode('yourFieldName', 'PFX')` — it does not reimplement the read-increment-write pattern. (`users.repository.firestore.js`'s `nextUserCode()` was refactored in Milestone 3 to call this instead of its own duplicate transaction, for exactly this reason.)
- `firestore.rules` gates who may write to `meta/counters` per the roles that can create a code-bearing entity — see the rules file itself, and `canManageStudents()` specifically for how a shared counter can be opened up to more than one role without loosening anything else.

## Future Firestore Hierarchy (documented for architectural guidance — not implemented)

As more of a student's data moves to Firestore in later phases, the natural structure is subcollections nested under each student document, rather than flat top-level collections cross-referencing a `studentId` field the way IndexedDB stores do today:

```
students
  {studentId}
    attendance      — one document per marked session, replacing the flat `attendance` store's studentId filter
    feeHistory       — invoices/receipts scoped to this student, replacing `invoices$.forStudent()` / `payments$.forStudent()`
    certificates      — replacing `certificates$.forStudent()`
    documents         — replacing `documents$.forOwner()`
    achievements      — new; not modeled anywhere today
```

This is **not implemented in Milestone 3** — Students exists today as a single flat top-level collection, exactly mirroring the scope of this migration. It's documented here so the *next* module migration that touches any of Attendance, Fees, or Certificates starts from a stated intention rather than inventing a structure ad hoc, and so that decision gets made once, deliberately, rather than differently by whoever migrates each of those modules first.

**Trade-off to weigh when that phase arrives:** subcollections make "everything about this one student" a single, cheap, natural read, but make cross-student queries (e.g. "every invoice overdue school-wide," which `fees.service.js` relies on constantly today) require either a collection-group query across every student's `feeHistory` subcollection, or keeping a parallel flat collection for exactly those queries. That decision should be made explicitly when Fees actually migrates, with real query patterns in hand — not assumed now.

## Known Gaps

- `userCode` generation exists (`nextUserCode()` in `users.repository.firestore.js`) but nothing calls it yet — `settings.service.js`'s `createUser()` does not currently assign a `userCode` to a newly created user. Wiring this up is unfinished Document 6 (User Management) work, not part of this migration.
- The future hierarchy above is a proposal, not a commitment — it should be reconsidered, not assumed correct, when the module that would actually use it is scoped.
