## 3. Field Mapping — IndexedDB → Firestore

**Retained, unchanged (every field above except `studentCode`).** No field was renamed to match a generic example schema — the real app has a dozen-plus call sites depending on these exact names (`name`, `guardianPhone`, `level`, `admissionNo`, …); renaming them would have forced changes across Admissions, Attendance, Fees, Certificates, Reports and Batches, which are explicitly out of scope for this migration.

**Added:**
- `studentCode` — the new, permanent ERP-wide business identifier (`STU000001`), generated automatically inside `create()`/`createMany()`. No caller needs to request it.

**Deprecated:** none. `admissionNo` is *not* deprecated — see the distinction below.

### `admissionNo` vs `studentCode`

The Student entity now carries two different identifiers, deliberately:

| | `admissionNo` | `studentCode` |
|---|---|---|
| Represents | The Admissions reference for how this person joined | The permanent ERP-wide student identifier |
| Format | `NAT/ADM/26/0074` (existing format, unchanged) | `STU000001` |
| Generated by | `settings$.nextSequence('admission')` (IndexedDB, unchanged — Admissions is out of scope) | `nextCode('studentCode', 'STU')` (Firestore, new) |
| Generated when | An application is submitted, or a walk-in is enrolled | The student record is created |
| Used by | The Admissions module only | Every operational module, going forward |

**Future modules should reference `studentCode`, not `admissionNo`.** `admissionNo` never becomes, and was never intended to become, the ERP's master student identifier — it answers "what was this student's admission reference," not "who is this student."

### Fields carried forward with pre-existing gaps (not fixed by this migration)

Two inconsistencies already existed in the IndexedDB implementation and are carried forward unchanged, on purpose — fixing them wasn't asked for and isn't a consequence of the storage backend changing:

- `notes` — accepted by the CSV importer's field mapping (`import.service.js`) but never actually written to a student record by any create/update path. Silently discarded today; still silently discarded after this migration.
- `leftOn` — read by `analytics.service.js`'s `studentGrowth()` but never written by any current code path (leaver tracking actually uses `statusChangedOn`). Looks like a copy-paste artifact from the `staff` store, which does set `leftOn`.

## 4. Repository-Bypass Fixes (required for the migration to actually work)

Two call sites wrote directly to the IndexedDB `students` store instead of going through `StudentRepository`/`students$`. Left unfixed, both would have kept silently targeting the now-orphaned IndexedDB store after the swap — a broken feature, not just an inconsistency:

- **`admissions.service.js`'s `enrolApplicant()`** — the normal way a real student is created (an approved admission being enrolled) — hand-built a student object and wrote it via a raw `db.unit(['students', 'admissions', 'auditLog'], …)` transaction. Fixed to call `students$.create()` for the student half; the `admissions` record update and its business rules are untouched.
- **`students.service.js`'s `bulkAssign()`** — moving a group of students to another batch — wrote via a raw `db.unit(['students', 'auditLog'], …)` transaction. Fixed to call the new `students$.updateMany()` (a Firestore `writeBatch`, the same atomic-batch intent as the IndexedDB transaction it replaces).

**Consequence, stated plainly:** both operations previously wrote their student change and their audit-log row in one atomic transaction. Firestore (`students`) and IndexedDB (`auditLog`) are two different databases now, so that single-transaction guarantee no longer holds — the student write is committed first, and the audit write follows immediately after, not atomically with it. See §9 Risks.

## 5. Firestore Indexes

Single-field equality (`branchId`, `status`, `batchId`, `level`, `admissionNo`, `studentCode`) needs no pre-declared index — Firestore indexes every field automatically for equality queries. The following **composite indexes** are recommended for the compound queries this repository issues:

| Query | Fields | Used by |
|---|---|---|
| Composite | `status ASC, branchId ASC` | `active(branchId)` — the most common listing query, and everything built on it (`unassigned()`, `birthdaysIn()`, `countsByLevel()`) |
| Composite | `status ASC, batchId ASC` | `byBatch()` combined with active-student filtering in roster views |

Create these under Firebase Console → Firestore Database → Indexes (or `firestore.indexes.json` if the project later adopts the Firebase CLI) before relying on branch- or batch-scoped listings at any real scale — small collections may work without them during testing, but Firestore will reject the query outright once it decides an index is required.

## 6. Security Rules

See `firestore.rules`, `match /students/{studentId}` block. Summary **as of this
milestone** — the Owner role upgrade in v2.23.0 added Owner & Accountant to
every write row below (`student.edit`, `student.delete`) and to
`canManageStudents()`/`meta/counters`. See
`docs/architecture/IAM_ROLE_MODEL.md` for the current model.

| Operation | Who |
|---|---|
| Read | Administrator, Owner & Accountant, Teacher & Reception, Viewer — every provisioned, active user (all four roles hold `student.view`) |
| Create | Administrator, Teacher & Reception (`student.edit`) |
| Update (general fields) | Administrator, Teacher & Reception |
| Update (archive/restore — `deletedAt`/`deletedBy` only) | Administrator only (`student.delete`), enforced via a field-level rule so an editor without delete rights can't archive a student by editing it |
| Hard delete | Administrator only |

The shared `meta/counters` document (§ sequence generator) is now writable by `canManageStudents()` (Administrator + Teacher & Reception), widened from the previous Administrator-only rule so a Teacher & Reception account creating a student can still be issued a `studentCode`.

## 7. Migration Notes

- **No data migration ran.** The IndexedDB `students` store is left declared in `SCHEMA` but is no longer written to by any active code path (except demo/seed data — see below). No records were copied from IndexedDB into Firestore; Firestore's `students` collection starts empty.
- **Seed data was deliberately left untouched.** `js/data/seed.js`'s `seedStudents()` still writes synthetic demo students directly into IndexedDB (`db.putMany('students', …)`), not through `students$`. This was a conscious choice, not an oversight: Firestore is one shared collection for the whole school, unlike IndexedDB, which is private to each browser. Auto-seeding fake demo students into a shared cloud collection from any fresh browser profile would risk polluting real school data — a materially worse outcome than seed data simply becoming invisible to the (now Firestore-backed) Students module. The rest of the demo dataset that references these seeded student IDs (attendance, invoices, admissions samples, certificates) remains internally consistent with itself, since it's all still IndexedDB — only the Students module's own view of them is affected.
- **Audit logging stayed on IndexedDB**, consistent with Milestone 2's precedent for Auth/Users — every create/update/archive/restore/delete writes a row to the existing `auditLog` store via the same shape `Repository._audit()` already produced.
- **`students.service.js` required zero changes.** Every function in it — `enrol`, `updateStudent`, `assignToBatch`, `promote`, `setStatus`, `archive`, `deleteStudent`, `restore`, `profile`, `household(s)`, `listStudents`, `atRisk`, etc. — calls `students$` exactly as it did before; the repository swap underneath is invisible to it, confirming the "same public contract" requirement held in practice, not just on paper.

## 8. Future Enhancements

- Wire real server-side pagination into the Students list UI. `paginate()` exists on the repository (Firestore cursor-based) but nothing calls it yet — every listing still fetches the full collection and paginates client-side (`js/ui/table.js`), exactly as it did against IndexedDB. Fine at today's scale; worth revisiting if a school's roll grows large enough that fetching every student on every page load becomes a real Firestore-read cost.
- Wire up `userCode` generation in `settings.service.js`'s `createUser()` — the generator exists, nothing calls it (see the Data Model doc's Known Gaps).
- Reconsider the seed-data strategy for Students (and every future migrated module) once more of the app depends on Firestore — a developer-invoked "seed Firestore" utility, explicitly separate from the automatic local-first-run seeding, rather than trying to make one seeding path serve both a shared cloud collection and a private local database.
- The documented-not-implemented future subcollection hierarchy (`students/{id}/attendance`, `/feeHistory`, `/certificates`, `/documents`, `/achievements`) in the Data Model doc — evaluate for real when Attendance, Fees, or Certificates actually migrate.

## 9. Risks

- **Cross-database atomicity is gone for the two fixed repository-bypasses.** `enrolApplicant()` and `bulkAssign()` used to write their Students-store change and their audit/admissions bookkeeping in one IndexedDB transaction; they now write to Firestore first and IndexedDB second, sequentially, not atomically together. A failure between the two steps leaves the Firestore write committed and the IndexedDB follow-up (admission status, audit row) not applied — recoverable by a human, but no longer impossible by construction the way it was.
- **`enrolApplicant()`'s double-click protection is weaker.** The original single-transaction design also incidentally prevented a rapid double-click from enrolling the same admission twice. Without that transaction, two near-simultaneous calls could both pass the "not yet enrolled" check before either write lands, and create two Firestore student records for one admission. Not fixed here — doing so properly would mean distributed locking or an idempotency key, which is a real design task of its own, not a "smallest safe change." Flagged for a follow-up, not silently accepted without disclosure.
- **The search-fallback path reads the entire collection.** `search()`'s substring fallback (used when the `searchKey` prefix range doesn't return enough hits) fetches every student, same as the IndexedDB version did. Fine at today's scale; a real Firestore-read cost concern if the roll grows large.
- **Firestore's per-read cost model applies where IndexedDB's did not.** Every `all()`/`active()` call is now a real network read against a metered service, not a free local query — worth monitoring as usage grows, in the same way flagged for Auth/Users in ADR-014.

## 10. Rollback Strategy

- The archived IndexedDB implementation (`js/data/archive/students.repository.indexeddb.js`) is a working, unmodified snapshot of `StudentRepository` as it stood immediately before this migration. Rolling back means re-pointing `js/data/repositories.js`'s `students$` export at it instead of the Firestore module, and reverting the two repository-bypass fixes (§4) back to their original raw `db.unit()` writes.
- No data-loss exposure: nothing was migrated *from* IndexedDB *to* Firestore, so a rollback loses only whatever real student records were created in Firestore since this shipped — those would need to be re-entered into IndexedDB if a rollback were ever executed after real use.
- As recommended in ADR-014 for future phases: consider gating the repository choice behind a config flag before the *next* module migration ships, so a future rollback is a configuration change rather than a code revert. Not retrofitted onto this migration.
