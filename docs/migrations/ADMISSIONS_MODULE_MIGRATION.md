# Module Migration Record — Admissions → Cloud Firestore

**Milestone:** 5
**Date:** 2026-07-24
**Status:** Implemented, pending manual UAT and approval (not committed, merged, or deployed)
**Related:** [ADR-014](../architecture/adr/ADR-014-Firebase-Authentication-and-Firestore.md), [STUDENT_MODULE_MIGRATION.md](STUDENT_MODULE_MIGRATION.md) (the template this record follows), [Firestore Data Model — Identifiers & Document Structure](../architecture/firestore-data-model.md)

## 1. IndexedDB Schema (before)

Store: `admissions` (see `js/config/app.config.js` → `SCHEMA.stores.admissions`)

- **Key path:** `id` (app-minted, `ADM-<timestamp>-<seq><random>` via `js/utils/id.js`'s `uid('ADM')`)
- **Indexes:** `branchId`, `status`, `appliedOn`, `searchKey`
- **Repository:** `AdmissionRepository` (extended `Repository`, `js/core/repository.js`) — archived, not deleted, at `js/data/archive/admissions.repository.indexeddb.js`

**Not migrated:** `admissionDrafts` (`AdmissionDraftRepository`/`drafts$`) — stays on IndexedDB. Drafts are half-typed forms: never audited, never soft-deleted, and out of this migration's scope, same as `auditLog` stayed on IndexedDB when Users and Students migrated.

## 2. Firestore Schema (after)

Collection: `admissions`

- **Document ID:** Firestore auto-generated (`addDoc`) — internal only, never displayed.
- **Fields:** every field the IndexedDB record had, unchanged — `name`, `dateOfBirth`, `gender`, `school`, `address`, `guardianName`, `guardianRelation`, `guardianPhone`, `guardianEmail`, `alternatePhone`, `occupation`, `branchId`, `level`, `preferredBatchId`, `priorExperience`, `yearsOfPractice`, `previousGuru`, `experienceNotes`, `medicalNotes`, `consentPhotography`, `feePlanId`, `feeNotes`, `docIdProof`, `docBirthCertificate`, `docPhotograph`, `documentNotes`, `applicationNo`, `status`, `appliedOn`, `submittedBy`, `reviewStartedOn`, `reviewedBy`, `approvedOn`, `approvedBy`, `approvalNote`, `rejectedOn`, `rejectedBy`, `rejectionReason`, `reopenedOn`, `enrolledOn`, `enrolledBy`, `studentId`, `searchKey`, `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `deletedAt`, `deletedBy`.
- **Repository:** `js/data/admissions.repository.firestore.js`, exported as `admissions$` from `js/data/repositories.js` (unchanged import path for every caller).

## 3. Field Mapping — IndexedDB → Firestore

**Retained, unchanged — every field.** No field was renamed. No new business-identifier field was introduced, unlike Students (which gained `studentCode`): Admissions already has a real, human-facing business identifier in `applicationNo`, so nothing was missing to add.

### `applicationNo` — deliberately not moved to the centralized sequence generator

`applicationNo` (`NAT/APP/26/0007`-style) continues to be generated by `settings$.nextSequence('application')` — IndexedDB, unchanged — rather than the Firestore `sequenceGenerator.firestore.js`'s `nextCode()` (which produces flat codes like `STU000001`). Two reasons, both deliberate:

1. **The format is genuinely different** — a year-scoped sequence (`NAT/APP/<year>/<seq>`), not a flat incrementing code. Moving it to `nextCode()` would change the visible format families see on applications, an unrequested behaviour change.
2. **No new cross-database risk is introduced.** `submit()` already called `settings$.nextSequence('application')` (IndexedDB) and then `admissions$.create()` (also IndexedDB, before this migration) as two separate, non-atomic calls — a gap in numbering was already possible if the second call failed, even before Firestore was involved. After this migration, the same two calls happen in the same order; only the second one now targets Firestore instead of IndexedDB. Nothing about the numbering's existing risk profile changes.

The same reasoning applies to the student's own `admissionNo` (`NAT/ADM/26/0074`-style, from `settings$.nextSequence('admission')`), generated inside `enrolApplicant()` — also unchanged, also already established as staying on IndexedDB since the Student migration (Milestone 3).

## 4. Repository-Bypass Fix (required for the migration to actually work)

**`admissions.service.js`'s `enrolApplicant()`** closed an approved application (marking it `ENROLLED`, stamping `studentId`) via a raw `db.unit(['admissions', 'auditLog'], …)` IndexedDB transaction — flagged as a known bypass in `STUDENT_MODULE_MIGRATION.md` §4 at the time, left alone because Admissions was out of that migration's scope. Left unfixed here, it would have kept silently targeting the now-orphaned IndexedDB `admissions` store. Fixed to call `admissions$.update()` for the admission half; the audit-log write (still IndexedDB — `auditLog` isn't migrating) now happens as a second, sequential call immediately after, instead of inside the same transaction.

**Consequence, stated plainly:** this was already a two-step, cross-database operation from the student side since Milestone 3 (`students$.create()` targets Firestore, the original `db.unit()` targeted IndexedDB for the admission+audit half). Now that the admission half also targets Firestore, the *admission update* and the *audit row* are the two steps that are no longer atomic with each other — the admission is closed first, so a failure writing the audit row leaves an enrolled application without an audit entry, rather than an application stuck mid-enrolment. See §9 Risks for the pre-existing double-click risk this does **not** newly introduce or fix.

## 5. Firestore Indexes

Single-field equality (`branchId`, `status`, `appliedOn`, `applicationNo`) needs no pre-declared index. No composite queries are issued against this collection today (every listing/report/analytics caller fetches `all()`/`pending()`/`byStatus()` and filters client-side, matching the IndexedDB version's own behaviour) — no composite index is required at this migration's scale. Revisit if a future branch- or status-scoped compound query is added.

## 6. Security Rules

See `firestore.rules`, `match /admissions/{admissionId}` block. Summary **as of
this milestone**, and two later changes have moved it: Hard delete was opened to
Administrator on 2026-07-27 so restore-from-backup could work, and the Owner role
upgrade in v2.23.0 granted Owner & Accountant `admission.edit`, so it now holds
Create as well as Update. See `docs/architecture/IAM_ROLE_MODEL.md` for the
current model.

| Operation | Who |
|---|---|
| Read | Administrator, Owner & Accountant, Teacher & Reception, Viewer — every provisioned, active user (all four roles hold `admission.view`) |
| Create | Administrator, Teacher & Reception (`admission.edit` — the only capability `submit()` requires) |
| Update | Administrator, Owner & Accountant, Teacher & Reception (the union of `admission.edit` and `admission.approve` holders) |
| Hard delete | Denied outright — no code path calls it today |

**Known, disclosed simplification:** unlike Students' field-level split between general edits and archive/restore, `admissions`' `update` rule does not distinguish *which* service-level action (review/approve/reject/reopen/enrol) produced a given write — it draws the one boundary that matters server-side today: Viewer can never write to this collection, and every other role's write is bound by whatever `admissions.service.js` itself still enforces client-side (status transitions, required fields). Replicating the full client-side state machine as field-level rules is a real design task, not attempted here as part of a "minimal and safe changes" migration — flagged as a future enhancement (§8) rather than silently left unmentioned.

## 7. Migration Notes

- **No data migration ran automatically.** The IndexedDB `admissions` store is left declared in `SCHEMA` but is no longer written to by any active application code path (except demo/seed data — see below). Firestore's `admissions` collection starts empty; see `ADMISSIONS_DATA_MIGRATION.md` for the optional one-time console utility.
- **Seed data was deliberately left untouched.** `js/data/seed.js`'s `seedAdmissions()` still writes synthetic demo applications directly into IndexedDB (`db.putMany('admissions', …)`), not through `admissions$` — the same conscious choice made for `seedStudents()` in Milestone 3: Firestore is one shared collection for the whole school, and auto-seeding fake demo applications into it from every fresh browser profile would risk polluting real school data.
- **Audit logging stayed on IndexedDB**, consistent with every prior migration — every create/update/archive/restore writes a row to the existing `auditLog` store via the same shape the base `Repository._audit()` already produced.
- **`admissions.service.js` required no changes beyond the one repository-bypass fix (§4).** Every other function — `submit`, `updateApplication`, `beginReview`, `approve`, `reject`, `reopen`, `eligibleBatches`, `pipeline`, `stalled`, `listApplications`, `applicationDetail` — calls `admissions$` exactly as it did before; the repository swap underneath is invisible to it.
- **`admissions.page.js` (UI) required zero changes.** Confirmed by inspection: it only ever calls functions exported from `admissions.service.js`, never `admissions$`, `db`, or the Firestore SDK directly.
- **Cross-database write, now resolved for one half:** `STUDENT_DATA_MIGRATION.md`'s "Known temporary architecture limitation" section previously flagged that `enrolApplicant()` split its write across Firestore (Students) and IndexedDB (Admissions), promising this would change once Admissions itself migrated. That section has been updated (see that file) to reflect what actually changed: both writes now target Firestore, but remain two sequential calls rather than one atomic transaction — see §8 for why a true cross-collection transaction wasn't attempted in this pass, and §9 for the risk this leaves unresolved.

## 8. Future Enhancements

- **A true atomic `enrolApplicant()`.** Now that both `students` and `admissions` live in the same Firestore project, a single `runTransaction()` spanning both collections is technically possible for the first time (it wasn't, when one side was IndexedDB and the other Firestore). Not implemented here: doing so correctly means either exposing a new cross-repository transaction primitive or having a Service touch the Firestore SDK directly, and the latter would break the "Firebase SDK isolated to Repositories/Providers" rule this whole architecture has held to since ADR-014. Worth a dedicated design pass, not a side effect of this migration.
- **Field-level security rules matching the full admission-status state machine** (§6) — evaluate once a real need (or incident) makes the current broad `update` rule insufficient.
- **`applicationNo`/`admissionNo` generation via the centralized `nextCode()` generator**, if `settings$` (and the Settings module generally) ever migrates to Firestore — revisit the format-change question at that point, not before.
- Wire real server-side pagination into the Admissions list UI, same as noted (and equally not done) for Students.

## 9. Risks

- **The pre-existing double-click risk on `enrolApplicant()` is unchanged, not newly introduced.** `STUDENT_MODULE_MIGRATION.md` §9 already flagged that removing the single-IndexedDB-transaction guarantee weakened protection against a rapid double-click enrolling the same admission twice. This migration doesn't make that risk worse (the admission-closing step was already outside any transaction with the student-creation step since Milestone 3) — it also doesn't fix it. A real fix (distributed locking, an idempotency key, or the atomic transaction in §8) is a design task of its own.
- **Cross-database atomicity between the admission update and its audit row.** See §4 — a failure between the two leaves an enrolled application without an audit trail entry, recoverable by a human, not automatic.
- **The search-fallback path reads the entire collection**, same as Students' — fine at today's scale, a real Firestore-read cost concern if application volume grows large.
- **Firestore's per-read cost model applies where IndexedDB's did not** — every `all()`/`pending()`/`recent()` call (used heavily by the dashboard, reports, and analytics screens) is now a metered network read, worth monitoring as usage grows.

## 10. Rollback Strategy

- The archived IndexedDB implementation (`js/data/archive/admissions.repository.indexeddb.js`) is a working, unmodified snapshot of `AdmissionRepository` as it stood immediately before this migration. Rolling back means re-pointing `js/data/repositories.js`'s `admissions$` export at it instead of the Firestore module, and reverting the `enrolApplicant()` fix (§4) back to its original raw `db.unit()` write.
- No data-loss exposure: nothing was migrated *from* IndexedDB *to* Firestore automatically, so a rollback loses only whatever real admissions were created in Firestore since this shipped — those would need to be re-entered into IndexedDB if a rollback were ever executed after real use.
- As already recommended in ADR-014 and repeated at the end of `STUDENT_MODULE_MIGRATION.md`: consider gating the repository choice behind a config flag before the *next* module migration ships, so a future rollback is a configuration change rather than a code revert. Not retrofitted onto this migration either.
